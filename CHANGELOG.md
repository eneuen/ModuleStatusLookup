# Changelog

All notable changes to this module are listed here. Versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

Added:

- **The lookup line's number.** On install the module takes internal number 2300, or the first free number up to 2399, and registers it in the PBX's extensions as a module number. It then appears as "Module: Status Lookup (2300)" in the PBX's destination pickers (incoming routes, IVR menus) while the module is enabled, and is hidden while it is disabled. 2300 is used because the PBX numbers its own IVR menus, queues and applications from 2200100 up, so 2200 would be a prefix of them. A reinstall that keeps settings keeps the number; an uninstall without kept settings releases it, unless a route still points at it. A later fresh install takes such a left-over number back, so those routes work again. The module never takes over a number another extension or module owns, and writes dialplan only for a number registered to it.
- **The module page** (administrators only, Modules → Status Lookup), Call Flow tab:
  - the line's state at a glance (answering on its number, or not, and what is missing), with Switch On and Switch Off. The line can only be switched on when it has an operator destination and every prompt can be played, and a change that would break a line that is on is refused;
  - Test Call: choose an extension and the PBX rings it; answering puts you through the line exactly as a caller hears it. The module's worker places the call (the web page has no connection to Asterisk), and it is logged as a test call from that extension, left out of Activity and the guessing protection;
  - where callers come from: the incoming routes, IVR menus and off-work rules that send callers to the line, and Change Number. A number something still sends callers to can't be given up: the change is refused and nothing moves;
  - what callers hear: each prompt from the built-in ones (only those with a recording) or the PBX's sound files, in a searchable menu with a play button on every entry and a Listen button beside it;
  - how callers type (shortest and longest ID, how long to wait for keys, tries; new lengths that would leave existing records out of reach ask first, naming how many), where callers go (operator, after the last try, when a lookup fails; the last two default to the operator) from the PBX's own destination list, and the guessing protection limits.
  Every value is checked again on the server; a refused change says what to fix, in English or Russian.
- **Page behaviour:** every action button ignores a second click while it works; a menu whose choice no longer exists (a deleted sound file or destination) shows it as missing instead of quietly picking another; the status dialog starts with no sound file chosen; the page works with any interface language, including ones written with an underscore (pt_BR, zh_Hans). Changes are written in transactions that take the database's write lock first, so a change made while calls are being logged waits a moment instead of failing.
- **Statuses tab:** the statuses records can have, in the order staff see them, each with its sentence (a PBX sound file, with a play button), what is said after it (nothing, the ID read back, or the record's date), what happens next (offer 1 to repeat and 0 for a person, say goodbye, or put the caller straight through to a destination) and how many records have it. Add, edit, move up and down, delete. Changing a status's code changes it on its records too; a status records still use is deleted only after choosing the status its records move to, in one step. A status whose sound file or destination has gone is flagged. Up to 50 statuses.
- **Business templates.** On first use the Statuses tab asks "What kind of business is this?" and offers IT and device repair, auto workshop, pharmacy, and retail and e-commerce, each with its usual statuses and ID lengths, or starting from scratch. A template adds its statuses with the wording to record for each (in English or Russian, following the PBX's language); Download Wording gives the list to whoever records them, and each status shows "Not recorded yet" with its wording until a sound file is chosen. Statuses that need a conversation (such as "Can't be repaired") put the caller straight through to the operator when one is set, and otherwise offer the repeat menu, where 0 reaches the operator. Add from Template… later adds only the statuses that are missing (by code) and changes nothing else; a template sets the ID lengths only while there are no records. On the Records tab, a status whose sentence isn't recorded yet carries a warning: callers with it are put through to a person. Templates are JSON files in `Setup/templates/`, checked strictly when read, so new industries can be added as files. Each status also has an optional wording field, for whoever records it.
- **Records tab** (the page's first tab): every record, newest change first, 50 to a page, with its ID, status (a coloured label), date, last day (expired records greyed, with the day they expired), note, and when, by whom and how it last changed. Search by ID (from the start, so 104 finds 10445) or by text in the note; filter by status, by "not changed in 7, 30 or 90 days", and expired only. Add and edit in a dialog (the ID must be within the call flow's ID lengths, and unique); select records to change their status or delete them together (up to 1,000 at a time). Export CSV downloads the filtered records in the import format; PINs are never exported, and a note a spreadsheet would run as a formula is prefixed with an apostrophe.
- **Import tab:** load records from a CSV file (UTF-8, comma- or semicolon-separated, with a header row; lookup_id and status_code are needed, note, expires, date, pin and phone optional; up to 5 MB and 100,000 rows). Drop the file or choose it, pick Add and Update or Replace All, and Check File shows what would happen first: how many records are new, changed, unchanged and deleted, and every row left out with its row number and reason (no ID, ID too short or long, the same ID as an earlier row, unknown status, note too long, a PIN that isn't 4 to 8 digits, a phone that isn't a phone number, a date that isn't YYYY-MM-DD). Nothing changes until Import is pressed; Replace All asks before deleting records not in the file, keeps records whose row in the file was left out (a typo in one row never deletes that customer's record), and is refused when no row in the file can be imported. Blank lines before the header are ignored. An ID keeps only its digits (TK-10445 becomes 10445), status codes match in any case, and a quoted note may span lines; the apostrophe Export CSV puts before formula-like notes is removed, so an exported file imports back unchanged. The whole file is applied in one transaction, so a call during the import sees the records as they were before or after it. Past imports are listed with who imported which file and what changed, and the rows each one left out. The file is read from the upload and never stored. A Download Example button gives a file in the right format.
- **The call flow.** A caller who reaches the line hears a welcome, types an ID and #, and hears its status: one recorded sentence, optionally followed by the ID read back or a date (weekday, month and day, in the PBX's language). After the status the line either says goodbye, offers "1 to hear it again, 0 to speak to someone", or sends the caller straight to the status's own destination. 0 at the ID prompt reaches the operator destination; an invalid entry, an unknown ID or an expired record costs a try, and after the last try (3 by default) the caller goes to the too-many-tries destination. A status whose destination no longer exists, or that can't be played, sends the caller to the fault destination, as does a lookup that fails for any reason (even when the lookup script can't run at all); if that destination is gone too, they hear an apology. Until the line is switched on and has an operator destination, it doesn't answer, so an incoming route moves on to its next rule or default action as for any unanswered destination.
  - The dialplan plays the prompts and collects the digits; a short AGI script runs once per try, looks the ID up (digits within the configured length only, one indexed read, bound parameters) and returns the result in channel variables. PHP is in the call for milliseconds, and a caller who hangs up leaves no PHP process behind.
  - The line behaves like the PBX's own IVR menus: it has its own row in the call history, tells the incoming route the call was answered (so the caller doesn't fall through to the route's next rule or default action), and takes transfers from phones. Its own 2-minute limit replaces the incoming route's ring timeout, which the PBX would otherwise apply to it, and is cleared before the caller is sent on, so a conversation is never cut short. A caller still in the lookup at the limit is sent to the too-many-tries destination (or said goodbye to, if they have heard their status), not cut off. The lookup part of a call isn't recorded: callers type IDs there.
  - Callers can press keys over the prompts that expect them: an ID typed during the welcome, or after "not found" before the ID prompt has finished, counts, and 0 during the status sentence reaches the operator. (The ID read back after the status doesn't listen for keys.)
  - IDs are digits, kept as text, so leading zeros count (`00451` and `451` are different records), and are 2 to 20 digits long, so 0 alone always means "speak to someone". An ID ends with # or the digit timeout; there is no digit limit, so extra digits are rejected with the entry rather than carried into the next try.
  - A record whose last day isn't a valid date counts as expired.
- **Miss limits** against guessing: a caller number (withheld numbers share one) that typed 10 IDs in the last hour that weren't found (or had expired), or all callers together reaching 200, is sent straight to the operator destination. An empty or malformed entry costs a try but isn't a miss, so silent callers can't push withheld callers to the operator. Test calls don't count; 0 turns a limit off.
- **Activity tab:** for the last 7, 30, 90 or 365 days or any period up to a year, in PBX time: calls, how many heard their status, the share that needed no person (heard a status and ended without reaching anyone) and how many were put through to a person, each against the previous period of the same length; calls by day; how calls ended; the busiest hours; the IDs callers typed most often that weren't found or had expired, each with Find in Records; and the call log (when, caller, ID typed, how it ended, status, where the caller was sent, tries, length), filterable by how calls ended. Test calls are left out of the numbers and marked in the log. Charts use a tree-shaken Apache ECharts 6.1.0. Every date and time on the page is shown in the PBX's time zone.
- **Built-in prompts** (welcome, enter ID, enter PIN, invalid, not found, repeat menu, goodbye, transfer, fault) are the default for every prompt, played in the PBX's language, or in English for languages the module has no recordings for. The recordings themselves are still to come.
- **Call log.** Every visit to the line is logged once, also when the caller hangs up in the middle, and also a second visit in the same call (an IVR menu option that leads back to the line) with its own tries and misses: a hangup handler, or the line itself just before it sends the caller on, hands the call to the module's worker, which validates it again, drops a visit it already has (a hang-up during the hand-off makes the line try again), and stores how it ended, the tries and misses, the last ID entered, the status and where the caller was sent. Daily counts per outcome, without phone numbers, are kept alongside.
- **PINs and caller-ID checks.** A status can ask for the record's PIN before it is told, and a status can be told only to a caller calling from the record's own phone number; both are switched on per status (Who Hears It, in the status dialog), and the pharmacy template asks for PINs on all its statuses.
  - A record's PIN (4 to 8 digits) is set in the record dialog or by an import's `pin` column; it is stored only as a keyed hash (HMAC-SHA256) and can't be shown or exported. Leaving the PIN empty keeps the current one; Remove the PIN clears it. The key is a random secret in `db/pin.key`, readable only by its owner, created on first use and kept when the module is reinstalled with its settings; the module makes it owner-only again after the PBX resets module files' rights on install.
  - The caller types the PIN after the ID; the lookup script collects it itself, so the digits never reach Asterisk's log. A wrong PIN is heard as "not found" and counts as a miss for the guessing protection; a record without a PIN on a status that asks for one puts the caller through to the operator.
  - A record's phone number is set in the record dialog or by an import's `phone` column (digits only, up to 20; spaces, dashes, brackets and a leading + are dropped). The caller's number matches when its last digits agree with the record's (at least 7, up to 9), so 04915112345678 and +4915112345678 are the same phone. A caller from another number, or a record without a phone, is heard as "not found" and counts as a miss.
  - The Records tab marks records with a PIN and shows their phone number; Export CSV writes the phone number.
- **REST API** (v3, under `/pbxcore/api/v3/module-status-lookup/`) for shop, POS or ticketing software: list, read, create or change (PUT by ID: fields left out keep their value) and delete records, import a CSV (add and update, with a dry run), replace all records (a separate resource, so API keys are granted it separately), and read the statuses and the activity totals. Every check is the page's own, so the API can't store anything the page couldn't; unknown fields are refused. Records changed through the API are marked "API" with the key's description. The calls run in the PBX's API worker; imports may take up to 2 minutes. The README describes the calls and how to give an API key access.
- **Privacy settings** (Call Flow tab): how long the call log keeps calls (by default as long as the PBX keeps its call history, which under 30 days means for ever, as in the PBX itself), and whether expired records are deleted every night. The module's worker runs the clean-up at 03:00 PBX time (and a minute after it starts), by whole day; the daily totals stay. **Forget Someone's Data** deletes one ID's record and every call that typed it, or every call from one caller number and that number on records (matched on the last digits, as for the caller-ID check); the PBX's system log notes who did it, without the ID or number.
- **Protection of what the line uses:** the PBX refuses to delete a sound file the line plays, or an extension, queue or IVR menu it sends callers to.
